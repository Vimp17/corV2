# Подключение источников API и прогнозных моделей

Это руководство описывает API-контракты именно текущей версии backend. Внешние API не следует подключать напрямую из n8n к БД: n8n оркестрирует вызовы, а PostgreSQL меняет только FastAPI.

## 1. Общая схема ежедневного процесса

1. Планировщик n8n запускает workflow по расписанию и получает перечень скважин из FastAPI.
2. В pull-режиме `POST /api/v1/monitor/run` для списка скважин или `POST /api/v1/monitor/wells/{well_id}/analyze` для одной скважины сами обновляют источники и запускают анализ. В push-режиме DARS/ХИМИК/ERA заранее отправляют нормализованные данные в ingestion endpoints; ежедневный `/monitor/run` затем использует сохранённые данные.
3. Backend проверяет наличие и достаточность телеметрии. Если минимальные требования readiness не выполнены, анализ риска и вызов LLM не выполняются; в ответе возвращаются причины и список запрошенных данных.
4. Модели из Registry рассчитывают результаты независимо. Сравнивайте только оценки одинакового смысла и шкалы.
5. Для скважин, попавших под правила оповещения, workflow загружает внешние сведения и вызывает LLM-отчёт.
6. Dashboard показывает расчёты и справку. LLM не бронирует бригаду и не создаёт наряд; итог утверждает инженер.

Схема входных требований к телеметрии настраивается в `.env`: `MAI_MIN_TELEMETRY_RECORDS`, `MAI_MIN_TREND_OBSERVATIONS`, `MAI_MIN_CURRENT_SIGNALS`, `MAI_MAX_TELEMETRY_AGE_HOURS`. Текущие обязательные поля записи — временная отметка `timestamp` и минимум несколько актуальных инженерных сигналов согласно readiness. Справочник канонических полей см. в `app/schemas.py` и профилях `config/source_profiles.json`.

## 2. API-контракты для передачи данных (push JSON)

Push-режим подходит, если источники сами вызывают backend после своей ежедневной выгрузки. URL ниже относительны к `http://<backend>:8000`. Если в `.env` задан `MAI_API_KEY`, во все запросы добавляется `X-API-Key: <значение>`. JSON кодируется в UTF-8; даты — ISO 8601, числа — в канонических единицах. Для повторной отправки той же пачки используйте тот же `batch_id` (идемпотентная загрузка).

### 2.1 DARS и ХИМИК: телеметрия

`POST /api/v1/ingestion/telemetry`

`source_id` должен совпадать с telemetry-профилем в `config/source_profiles.json`: обычно `DARS` либо `KHIMIK`. Каждый элемент `records` — одно наблюдение для указанной скважины. Дополнительные внешние столбцы отправляйте только после явного согласования; backend принимает канонические поля.

```json
{
  "well_id": "WELL-001",
  "source_id": "DARS",
  "batch_id": "DARS-WELL-001-2026-09-30",
  "records": [
    {
      "timestamp": "2026-09-30T08:00:00+03:00",
      "water_cut_pct": 71.4,
      "co2_pct": 0.8,
      "chlorides_mg_l": 18500,
      "inhibitor_efficiency": 0.76,
      "corrosion_rate_mm_year": 0.31,
      "wall_thickness_mm": 8.4
    }
  ]
}
```

Массив содержит минимум одну запись; endpoint принимает до 10 000 на вызов. Для одной скважины отправляйте серию измерений по датам, чтобы пройти readiness (по умолчанию требуется не менее 8 уникальных измерений и не менее 2 актуальных сигналов). Повторные отправки с тем же batch ID безопасны; обновлённые данные отправляйте с новым batch ID.

Пример PowerShell:

```powershell
$payload = Get-Content .\dars-payload.json -Raw
Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:8000/api/v1/ingestion/telemetry' `
  -ContentType 'application/json' -Body $payload
```

### 2.2 ERA: история работ и отказов

`POST /api/v1/ingestion/history`

`source_id` по умолчанию `ERA`; укажите его явно, если профиль переименован. Достаточно передать хотя бы один непустой массив. Работа требует `date` и `work_type`; отказ требует `failure_date` и `failure_type`.

```json
{
  "well_id": "WELL-001",
  "source_id": "ERA",
  "batch_id": "ERA-WELL-001-2026-09-30",
  "work_history": [
    {"date": "2026-05-10T10:00:00+03:00", "work_type": "Замена НКТ", "reason": "износ", "result": "работоспособность восстановлена"}
  ],
  "failure_history": [
    {"failure_date": "2026-05-08T07:30:00+03:00", "failure_type": "утечка", "equipment": "НКТ", "corrosion_detected": true, "downtime_days": 2}
  ]
}
```

Поля `reason`, `equipment`, `result`, `cause`, `corrosion_detected`, `repair` и `downtime_days` необязательны. Неизвестное значение оставляйте `null`/не включайте, не подставляйте догадку.

### 2.3 Расписание бригад

`POST /api/v1/ingestion/crew-schedule?well_id=WELL-001`

Endpoint принимает JSON-envelope с `crew_availability`. **Передавайте `well_id` отдельно для каждой скважины**: расписание хранится в контексте скважины. Не используйте `well_id=ALL`.

```json
{
  "crew_availability": [
    {
      "crew_id": "BRIGADE-17",
      "specialties": ["corrosion", "tubing"],
      "region": "Север",
      "status": "available",
      "available_from": "2026-09-30T12:00:00+03:00",
      "available_to": "2026-10-02T20:00:00+03:00"
    }
  ]
}
```

Требуется `crew_id`; `status` — `available`, `busy` или `unknown`. Для корректного выбора указывайте специализации, регион и интервал доступности. Можно передать до 5 000 записей. Отправка заменяет сохранённый снимок расписания для этой скважины и источника — синхронизируйте полный актуальный список, а не отдельные изменения. Для таблицы дежурств общего назначения upstream-посредник должен развернуть расписание в записи для каждой скважины либо предоставлять отдельную выгрузку на запрос со скважиной.

Пример:

```powershell
$payload = Get-Content .\crew-schedule.json -Raw
Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:8000/api/v1/ingestion/crew-schedule?well_id=WELL-001' `
  -ContentType 'application/json' -Body $payload
```

### 2.4 Получение данных API самим backend (pull)

Сейчас прямые переменные `MAI_SOURCE_DARS_URL`, `MAI_SOURCE_KHIMIK_URL`, `MAI_SOURCE_ERA_URL` означают не произвольный JSON API. Backend делает `GET <URL>?well_id=<id>` с необязательным Bearer-токеном и ожидает XLSX байты. Для расписания GET-путь ожидает JSON с массивом `crew_availability`.

Если внешняя система отдаёт JSON, нестандартный OAuth, POST или особую вложенность, есть два варианта:

1. Пусть интеграционный сервис/n8n преобразует upstream-ответ в каноническую JSON-структуру из раздела 2 и отправляет её на FastAPI push endpoints.
2. Сделайте Python-пакет `SourceAdapter`, зарегистрируйте entry point `mai_corrosion.sources`, добавьте в профиль в `config/source_profiles.json` ключ `adapter` с именем entry point, установите пакет в образ API и пересоберите его. Адаптер реализует `fetch_for_well(well_id, profile)` и возвращает JSON: телеметрия `{ "records": [...] }`; история `{ "work_history": [...], "failure_history": [...] }`; расписание `{ "crew_availability": [...] }`. Для специфичной авторизации/параметров используйте секреты окружения, а не записывайте токены в profile или код.

Проверка API статусов: `GET /api/v1/ingestion/sources`; проверка накопленных данных: `GET /api/v1/ingestion/wells/{well_id}/telemetry` и `/api/v1/ingestion/wells/{well_id}/history`; внешние расписания для AI-контекста проверяет `GET /api/v1/monitor/wells/{well_id}/external-data`.

## 3. Подключение новой модели прогноза риска

### 3.1 Контракт модели

Registry загружает встроенные `rules` и `cox`, затем установленные Python entry points группы `mai_corrosion.risk_models`. Плагин реализует контракт из `app/core/model_registry.py`: модель объявляет уникальные `model_id` и `model_version`, принимает `ModelInput` и возвращает `ModelPrediction`. Вход включает ID скважины, канонический `FeatureSnapshot`, нормализованные записи, горизонт прогноза и состояние Cox-модели. Результат содержит состояние, горизонт, тип шкалы и значение риска.

Используйте статусы `ok`, `unavailable`, `error`, `insufficient_data`, `unsupported_horizon` по ситуации. `probability` допустим только для оценки вероятности отказа с определённым горизонтом и проверенной калибровкой. Для score/баллов/относительного риска задавайте соответствующий `score_kind` и не называйте их вероятностью. При недостатке данных возвращайте `insufficient_data`, а не нулевой риск.

### 3.2 Минимальный пакет плагина

Создайте отдельный Python-пакет, например:

```text
mai-risk-example/
├── pyproject.toml
└── mai_risk_example/
    ├── __init__.py
    └── plugin.py
```

В `pyproject.toml` объявите entry point:

```toml
[project]
name = "mai-risk-example"
version = "0.1.0"
dependencies = []

[project.entry-points."mai_corrosion.risk_models"]
example = "mai_risk_example.plugin:ExampleRiskModel"
```

Класс `ExampleRiskModel` должен реализовать контракт Registry. Возьмите за образец `examples/model_plugin_template.py` и проверьте точные поля `ModelInput`/`ModelPrediction` в `app/core/model_registry.py`. Не копируйте коэффициенты Cox или демонстрационные правила как обученную производственную модель.

### 3.3 Установка в Docker

Подключите пакет к зависимостям API-образа (например, добавьте в `requirements.txt` локальный пакет, скопируйте его в Dockerfile, либо установите версионированный артефакт из внутреннего package registry). Закрепите версию, пересоберите API и проверьте:

```powershell
docker compose up -d --build mai-api
Invoke-RestMethod http://localhost:8000/health/ready
Invoke-RestMethod http://localhost:8000/api/v1/risk/models
```

Новая модель должна появиться в реестре; ошибки загрузки плагинов видны в `plugin_load_errors`. Затем запустите анализ тестовой скважины и убедитесь, что результат содержит ожидаемые `model_id`, `model_version`, статус, тип шкалы и горизонт.

### 3.4 Сравнение нескольких моделей и проверка

Все модели получают общий `ModelInput`, но их шкалы могут различаться. В dashboard результаты представлены рядом для анализа, но численно сравнивайте только сопоставимые величины: одинаковый горизонт, определение события и калибровка. Rule score 80/100 нельзя трактовать как вероятность 80%; relative risk нельзя напрямую сравнить с вероятностью.

Для оценки на исторических данных используйте `POST /api/v1/validation/landmarks` и передавайте `model_scores` (и `model_probabilities` только для калиброванных вероятностей). Смотрите ROC AUC/PR AUC, Brier score и метрики с учётом цензурирования, проверяйте временной holdout и отдельные периоды/объекты. Порог оповещения должен применяться к подтверждённой вероятности либо классу Rule Engine; добавление модели не означает автоматическую активацию её результатов для производственных решений.

## 4. Как фактически используется расписание в LLM сейчас

Backend собирает `crew_availability` через внешний контекст `/api/v1/monitor/wells/{well_id}/external-data`, а `app/core/agent.py` передаёт его в Chat Completions LiteLLM вместе с телеметрией/диагностикой, результатами риск-моделей, историей работ и отказов, статусами источников и схемой ответа. История ограничена последними 100 событиями каждого типа, список бригад — первыми 200 записями; применённые ограничения передаются модели.

До текущего изменения system prompt запрещал выдумывать доступность бригад и требовал сообщить, что расписание неизвестно, если оно не передано. Он **не содержал явной инструкции** выбрать рекомендацию по специализации/региону/окну доступности и объяснить конфликт расписания. Теперь prompt требует:

- учитывать только `status=available` и проверять интервал доступности;
- сопоставлять специализацию и регион с рекомендованной работой, если они представлены;
- объяснять соответствие или конфликт в `crew_schedule_comment`;
- не называть бригаду, если расписание этого не подтверждает; при отсутствии подходящей бригады оставить назначение/срок оператору;
- не трактовать `busy`/`unknown` как доступную бригаду и не откладывать срочное реагирование только из-за отсутствия бригады;
- не заявлять, что наряд или бронирование уже созданы.

Ограничение: расписание должно быть свежим и полным. Контракт содержит статус, специализацию, регион и доступное временное окно, но не цену, загрузку по часам, приоритеты диспетчера или реальные правила назначения. LLM генерирует текстовый план и комментарий, не оптимизирует расписание и не резервирует ресурс. Инженер проверяет рекомендации перед действием.

## 5. Настройка n8n

Для расписного запуска активируйте workflow `n8n/scheduled_risk_monitor.json`, задайте часовой пояс и целевое время ежедневного запуска. Credentials для FastAPI используют `X-API-Key`, если включён `MAI_API_KEY`. URLs должны смотреть на имя сервиса внутри Compose (`http://mai-api:8000`), а не `localhost`, поскольку localhost внутри контейнера — сам n8n.

Цепочка: Cron → `POST /api/v1/monitor/run` (обновление источников, readiness, анализ и рейтинг) → обработка рискованных скважин → получение внешнего контекста → запрос справки → результат в dashboard. Перед включением автоматического графика выполните workflow вручную на тестовой скважине, убедитесь в статусах источников, причине пропуска при плохих данных, записи справки в dashboard и отсутствии ложного утверждения о бронировании бригады. В push-схеме upstream-системы сначала загружают данные в FastAPI; n8n по расписанию выполняет анализ и выдачу отчётов.

## 6. Если внешние поля переименовали

Для Excel/pull меняйте aliases `field_map` в `config/source_profiles.json`: слева — внутреннее каноническое поле, справа — допустимые внешние заголовки. Не переименовывайте внутреннее поле без необходимости: модели, API и dashboard используют каноническую схему.

Для JSON/push настройте преобразование во внешнем API gateway, n8n Code/Set узле или SourceAdapter: внешнее имя преобразуйте в `timestamp`, `water_cut_pct`, `chlorides_mg_l` и другие имена из `TelemetryPoint`; историю — в `work_history`/`failure_history`; расписание — в поля `CrewAvailability`. Если добавляется действительно новый инженерный сигнал, обновите схему, нормализацию, Feature Engineering, проверки качества, примеры, тесты, документацию и версии моделей, которые умеют его потреблять. Сначала проверьте контракт через `/docs` и ingestion на тестовой скважине.

## 7. Безопасность и эксплуатация

- Не храните секреты в JSON workflow, source profile, prompt или примерах. Секреты API размещайте в `.env`/Docker secrets и credentials n8n.
- Используйте TLS для production API и ограничьте `MAI_API_KEY` сетевым доступом и правами вызова.
- Перед загрузкой новых моделей закрепляйте их версии, сохраняйте артефакты отдельно и проверяйте совместимость/лицензии.
- Для production нужны метрики свежести источников, расписания резервного копирования PostgreSQL, мониторинг ошибок плагинов и журнал утверждений инженера.
- Демонстрационные Rule Engine/Cox и синтетические данные не являются подтверждёнными производственными прогнозами; потребуется валидация на реальных исторических данных.
