# План упрощения кодовой базы

Дата: 17.11.2026. Проверенная версия: `2708e6a`, ветка `codex/response-rules-demo`.

Статус: этапы 0–4 согласованы пользователем 17.11.2026; реализация и проверка выполняются в ветке `codex/simplify-codebase`.

## Вывод

Большого объёма заведомо неиспользуемого кода не обнаружено. Есть остатки прежней реализации агента, несколько невостребованных функций и повторяющиеся участки подключения источников. Их можно убрать без сокращения функций продукта. Массовое удаление модулей означало бы отказ от поддерживаемых сценариев.

Проверены состав отслеживаемых файлов, определения и ссылки на функции, импорты, API, вызовы из интерфейса и n8n, конфигурация, тесты и Windows-упаковка. Статический поиск дополнен разбором путей генерации предложений, проверки/импорта источников, обработки документов и расчётов. Это не измерение частоты использования на реальном стенде: статистика обращений и данные остановленной БД не анализировались. Поэтому «редко используется» не считается достаточным основанием для удаления.

Размер по отслеживаемым исходникам, включая комментарии и пустые строки:

## Участок для локального упрощения

`app/core/source_connectors.py`: `_from_url()` и `check_source()` повторяют получение URL, его проверку, загрузку ответа, обработку пустого ответа и преобразование JSON расписания. Выбор и вызов адаптера также повторяются в проверке и импорте.

Предлагается общий небольшой внутренний путь получения ответа в этом же модуле. Проверка без записи и сохранение данных остаются отдельными операциями. Существующие `check_source()`, `refresh_sources_for_well()`, `SourceAdapter.fetch_for_well()` и HTTP-контракты сохраняются.

Условия принятия изменения:

- Меньше повторяющегося кода и развилок, без новых классов, зависимостей или дополнительных архитектурных слоёв.
- Проверка источника не меняет данные, рейтинг и статусы в БД.
- Сохраняются таймауты, ограничение размера, повторы временных ошибок, запрет редиректов, скрытие секретов и понятные ошибки.
- Сохраняются идентификаторы пакетов, принадлежность строк скважине, происхождение данных, пустое расписание как очистка и поведение HTTP 404.
- Если общий путь потребует множества флагов или изменит результаты проверки/импорта, от такого объединения отказываемся.

## Что сохраняем

| Участок | Почему он нужен |
| --- | --- |
| НТЦ, математическая модель, автоматический NORSOK и администраторские подстановки | Это действующие функции; объединение разных формул ради меньшего количества файлов усложнит их проверку |
| Импорт v4, базовый расчёт v4, файловый расчёт NORSOK и история CO₂ | Доступны через API, описаны в документации и покрыты тестами. Отсутствие формы на главном экране не означает отказ от API |
| PDF, OCR, фотографии, `.xls`, `.xlsx`, реестр НКТ и дополнительные показатели | Разные входные форматы и правила подтверждения данных. Общая таблица не заменяет специализированные читатели |
| `pyodbc` и `pymssql` | Поддерживают разные способы подключения SQL Server, включая Windows-аутентификацию и работу без установленного ODBC |
| n8n, push API, HTTP pull, интерфейс адаптеров | Это действующие способы интеграции; адаптеры также нужны для обсуждавшегося подключения Промайн |
| Очередь документов, блокировки, повтор пересчёта, транзакции и миграция старых данных | Защищают от потери данных, гонок и неполного обновления; редкое исполнение не делает их лишними |
| Операторские поля, все столбцы рейтинга, график ППР, экспорт, настройки источников и Windows CLI | Поддерживаемые функции. Низкий приоритет операторских действий не означает согласие на их удаление |
| Поля ответа API и отображение старых предложений | Сохраняют совместимость с n8n, интеграциями и ранее записанной БД; например, `differs_from_rating` может встречаться в старых предложениях |
| Регрессионные тесты и проверки Windows/DLL/архива | Они проверяют существенные сбои, а не являются частью поставляемого backend |

Не включаем в этот этап дробление `dashboard/index.html` и больших читателей Excel только ради размера файлов: перенос строк сам по себе не облегчает кодовую базу. Не вводим общий фреймворк парсеров. Два почти одинаковых небольших валидатора в `app/schemas.py` оставляем: новое наследование ради нескольких строк принесёт больше связей, чем пользы. Аналогично не переносим парсер `.env` между backend и standalone: их поведение и обязанности различаются.

Все прямые runtime-зависимости имеют назначение. `pip` из переносимого Python не является прямой зависимостью приложения, но удалять части runtime в рамках этого рефакторинга не предлагается: это отдельный вопрос установки адаптеров и сопровождения сборки.

## Этапы реализации после согласования

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| 0. Зафиксировать поведение | Прогнать существующие тесты в изолированном окружении. До правок добавить недостающие проверки реального пути агента с реестром и равнозначности получения данных в проверке/импорте | Проверки проходят на исходной версии; каждый затрагиваемый сценарий имеет поведенческую проверку |
| 1. Удалить остатки | Невостребованные функции, импорты, логгеры, устаревшие CO₂-заготовки тестов; удалить файл примеров, настройку и пустой аргумент, актуализировать README | Нет обращений к удалённым элементам; результаты действующих сценариев прежние |
| 2. Упростить агент | Убрать ветку без реестра и повторное формирование полей; убрать лишние поля, запрашиваемые у LLM | LLM сохраняет собственные summary/reasoning; действия только из выбранных сработавших правил; проверки сроков, бригад, пустого выбора и режима demo/approved сохранены |
| 3. Убрать повторы подключения | Локально объединить получение ответа источника, оставив отдельными диагностику и запись | Матрица HTTP/адаптер × XLSX/JSON проходит; диагностика не пишет в БД, импорт идемпотентен, ошибки и источник данных сохранены |
| 4. Проверить и собрать | Полные Python/SQL-тесты с обоими драйверами, Node, браузерные сценарии, локальная сборка и GitHub Actions с Windows smoke | Все обязательные проверки успешны; ZIP проверен; итоговый diff и число удалённых/добавленных строк отражены в отчёте |

Перенос старых тестов `_check()` на контекст с реестром сохраняет их проверки занятости бригады, окна доступности и срока рейтинга. Это не повод удалять эти тесты. Для LLM используется ранее согласованный изолированный HTTP-имитатор; настоящий внешний сервис для этого этапа не нужен.

В этапах 0 и 4 допускаются только временные тестовые контейнеры с отдельной БД и удалением по окончании. Остановленный QA-стенд, его данные и контейнеры n8n/SQL Server не запускаются. Изменения в отдельной ветке; пользовательский `docker-compose.override.yml`, реальные `.env`, секреты и БД остаются вне изменений.

Ожидаемый эффект — убрать один неиспользуемый конфигурационный файл и несколько десятков/сотен строк, сократить развилки и повторения. Это оценка до реализации, не обещание процента сокращения. Формулы, схема БД и набор пользовательских возможностей не меняются.

## Конкретное согласование архитектурно чувствительных файлов

Согласно пользовательским AGENTS.md до таких правок требуется решение пользователя.

| Файл / контракт | Предлагаемое изменение | Влияние и более локальная альтернатива |
| --- | --- | --- |
| `app/config.py` | Удалить только `response_examples_path` / чтение `MAI_RESPONSE_EXAMPLES_PATH` | Параметр уже никем не используется; старые `.env` можно оставить без редактирования. Альтернатива — оставить неработающую настройку с пометкой, что сохраняет лишний код |
| `standalone/build/build_windows.py` | Удалить только неиспользуемый `TEXT_CRLF` | Алгоритм и манифест сборки не меняются. Удалённый файл примеров автоматически перестанет копироваться с каталогом `config/`. Альтернатива — сохранить мёртвую константу |
| `app/core/proposal_agent.py`, `proposal_language.py` — внутренний запрос к LLM | Удалить устаревшие примеры и запрашивание серверных полей; сделать реестр обязательным в текущем внутреннем пути | Формат HTTP API и сохранённые предложения совместимы. Альтернатива — оставить лишние инструкции и ветви, ограничиться только удалением файла |

Остальные изменения — локальные внутри существующих модулей. Не планируются изменения `app/schemas.py`, `app/db/schema.py`, миграций, `app/main.py`, `.github/workflows/build-demo.yml`, списка зависимостей и интерфейса адаптеров. Если реализация потребует их изменения, сначала будет подготовлено отдельное конкретное согласование.
