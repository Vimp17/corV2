# MAI Corrosion Control — backend и BI-дашборд

Проект принимает суточные данные скважин, проверяет качество, рассчитывает диагностические признаки и риск, а для рискованных скважин формирует справку через LiteLLM. **Оператор работает только с BI-дашбордом:** email-уведомлений в проекте нет. n8n запускает и соединяет этапы; расчёты и контракты данных находятся в FastAPI.

> Пороги и баллы текущего Rule Engine унаследованы из демонстрационного pipeline. Это индикаторы для проверки системы, не подтверждённая вероятность отказа и не производственная инструкция. Перед эксплуатацией пороги и модели необходимо проверить на фактических размеченных данных.

## 1. Проект по шагам

1. DARS, ХИМИК, ERA и система расписания подключаются через API. Встроенный pull-коннектор DARS/ХИМИК/ERA ожидает Excel `.xlsx`; JSON API подключается через SourceAdapter или передаёт канонические JSON-данные в FastAPI push endpoints.
2. FastAPI скачивает подключённые данные по API либо оператор загружает книгу через дашборд.
3. Ingestion читает нужные листы, сопоставляет внешние названия колонок с единым внутренним форматом, проверяет строки и сохраняет нормализованные поля в PostgreSQL.
4. Data Quality и readiness проверяют качество, свежесть и достаточность телеметрии. Если её мало, расчёт моделей и запрос к ИИ пропускаются; система сообщает, какие значения или какой источник нужны.
5. Feature Engineering и диагностики готовят единый контекст. Зарегистрированные модели считают свои оценки риска независимо друг от друга.
6. При высоком/критическом классе правил или превышении порога явно калиброванной вероятности backend отмечает скважину как рискованную.
7. Для таких скважин n8n получает паспорт анализа, историю работ/отказов и актуальное расписание бригад. Backend передаёт эти данные и результаты моделей LiteLLM по Chat Completions API.
8. Ответ модели проверяется по JSON-схеме, сохраняется в PostgreSQL и появляется рядом со скважиной в дашборде. ИИ не создаёт наряд, не бронирует бригаду и не заменяет решение инженера.

## 2. Запуск с Docker Compose (Windows)

### Шаг 1. Подготовить файлы и пароли

Установите Docker Desktop и запустите его. В PowerShell перейдите в каталог проекта, создайте локальный `.env` из примера и откройте его:

```powershell
Copy-Item .env.example .env
notepad .env
```

Замените `POSTGRES_PASSWORD` на свой пароль и укажите тот же пароль в `MAI_DATABASE_URL`. Для простоты используйте латинские буквы и цифры. Не публикуйте `.env` и не добавляйте его в архив/репозиторий. Оставьте адреса необязательных API и LiteLLM пустыми до подключения.

### Шаг 2. Запустить сервисы

Из папки проекта выполните:

```powershell
docker compose up -d --build
```

Первый запуск скачивает образы и устанавливает Python-зависимости. Убедитесь в статусе:

```powershell
docker compose ps
```

Проверка backend:

```powershell
Invoke-RestMethod http://localhost:8000/health/ready
```

Проверка API с документацией: откройте <http://localhost:8000/docs>. Дашборд: <http://localhost:8000/dashboard>. Редактор n8n: <http://localhost:5678>.

Если меняли `.env`, примените параметры перезапуском `docker compose up -d`. Если меняли Python-код или устанавливали новый плагин модели, пересоберите backend: `docker compose up -d --build mai-api`.

### Шаг 3. Подключить PostgreSQL

Compose автоматически создаёт два каталога данных в именованных томах и две БД в одном PostgreSQL:

- `mai_corrosion` — телеметрия, статусы источников, история, результаты анализа и AI-справки; API подключается к ней через `MAI_DATABASE_URL`.
- `mai_n8n` — внутренние credentials и рабочие процессы n8n. Настройку выполняет Compose через переменные `DB_POSTGRESDB_*`.

Вручную создавать таблицы не нужно: API создаёт их при старте. Данные сохраняются в Docker volume и переживают пересоздание контейнера. Для резервного копирования используйте `pg_dump` каждой базы и храните выгрузку отдельно от контейнера. Для просмотра из PowerShell можно открыть консоль PostgreSQL:

```powershell
docker compose exec postgres psql -U mai -d mai_corrosion
```

Основной порт PostgreSQL наружу не опубликован: API и n8n обращаются к нему по внутреннему имени `postgres`. Чтобы подключить существующую внешнюю БД, задайте `MAI_DATABASE_URL` в формате `postgresql+psycopg://пользователь:пароль@хост:5432/имя_базы`, разрешите сетевой доступ с хоста Docker и убедитесь, что пользователь может создавать и менять таблицы. Для PostgreSQL на машине-хосте из Compose обычно указывают `host.docker.internal` вместо `localhost`. Для пароля со спецсимволами используйте URL-кодирование.

### Шаг 4. Настроить внешние API данных

Встроенный pull-коннектор использует один HTTP GET на скважину: `GET <заданный URL>?well_id=<ID>`. Для DARS/ХИМИК/ERA это HTTP API, возвращающее Excel `.xlsx` в теле ответа; расписание возвращает JSON. Если задан токен, запрос содержит `Authorization: Bearer <token>`. Для upstream JSON, другого метода, OAuth или нестандартного контракта используйте SourceAdapter либо push endpoints. Подробные примеры JSON, регистрация адаптера и контракт моделей приведены в [API и модели: подробное руководство](docs/API_AND_MODELS_GUIDE.md).

В `.env` укажите переменные:

| Источник | URL | Необязательный Bearer token | Ответ |
| --- | --- | --- | --- |
| DARS | `MAI_SOURCE_DARS_URL` | `MAI_SOURCE_DARS_TOKEN` | `.xlsx`, профиль `dars` |
| ХИМИК | `MAI_SOURCE_KHIMIK_URL` | `MAI_SOURCE_KHIMIK_TOKEN` | `.xlsx`, профиль `khimik` |
| ERA | `MAI_SOURCE_ERA_URL` | `MAI_SOURCE_ERA_TOKEN` | `.xlsx`, профиль `era` |
| Расписание бригад | `MAI_SOURCE_CREW_SCHEDULE_URL` | `MAI_SOURCE_CREW_SCHEDULE_TOKEN` | JSON, контракт ниже |

Сами внешние системы должны принимать query-параметр `well_id`. Пример URL: `https://data.example.ru/api/export/dars`. После правки `.env` запустите `docker compose up -d` и проверьте **GET `/api/v1/ingestion/sources`** в <http://localhost:8000/docs> или `GET http://localhost:8000/api/v1/ingestion/sources`.

### Шаг 5. Подключить LLM через LiteLLM

Настройте LiteLLM Proxy отдельно (в этом Compose LiteLLM-сервис не запускается). В `.env` задайте:

```dotenv
MAI_LLM_API_URL=https://litellm.example.ru/v1/chat/completions
MAI_LLM_API_KEY=секретный_ключ
MAI_LLM_MODEL=имя_модели_в_LiteLLM
MAI_LLM_TIMEOUT_SECONDS=45
MAI_LLM_MAX_RETRIES=1
```

Backend вызывает `requests.post()` с OpenAI-совместимым JSON: `model`, `messages`, `temperature` и запрошенная JSON-схема отчёта. Токен передаётся только в `Authorization: Bearer ...`. У endpoint должны быть доступны Chat Completions, возврат содержимого assistant в `choices[0].message.content`, доступ к выбранному deployment и возможность сформировать JSON. Ответ должен включать `well_id`, `executive_summary`, `risk_interpretation`, `data_gaps`, `recommended_actions`, `crew_schedule_comment`, `human_review_required: true` и `disclaimer`; поля действий `priority/title/instruction/rationale/evidence/suggested_team/requires_human_approval` валидируются backend. При недоступном или выключенном LiteLLM оценки риска остаются доступны, а статус справки виден в BI.

После изменения конфигурации: `docker compose up -d mai-api`. В `/health/ready` проверьте `llm_agent: configured`; окончательный тест — запустить анализ рискованной скважины и проверить сохранённую справку в дашборде.

### Шаг 6. Настроить защиту API

По умолчанию `MAI_API_KEY` пуст и ключ не требуется. Для защиты задайте длинное случайное значение в `.env` и выполните `docker compose up -d`. На дашборде введите тот же ключ в поле **«Ключ API»**. В n8n создайте Credential типа **Header Auth** с именем заголовка `X-API-Key` и тем же значением, затем назначьте его каждому HTTP Request, который обращается к FastAPI. Не вставляйте ключ прямо в workflow JSON.

### Шаг 7. Импортировать и включить n8n

При первом открытии n8n создайте пользователя-владельца. Затем импортируйте файлы через меню **Workflows → Import from File**:

- `n8n/scheduled_risk_monitor.json` — ежедневное расписание;
- `n8n/well_analysis_operator.json` — ручная форма оператора.

Откройте каждый workflow, создайте/выберите API-key credential, если защита включена, и назначьте его HTTP Request узлам. Сохраните workflow. Включите (Activate/Publish) ежедневный workflow. Планировщик настроен на 07:00, часовой пояс берётся из `GENERIC_TIMEZONE` (по умолчанию `Europe/Moscow`). Нажмите **Test workflow** для ручной проверки формы. Примечание n8n расположено рядом с каждым узлом: оно описывает задачу, вход и выход.

Ежедневный мониторинг рассматривает скважины, уже известные базе, плюс ID из `MAI_WELL_IDS` (список через запятую). Для первого запуска сначала загрузите Excel или добавьте ID в `.env`. Если внешний API ещё не настроен, статус будет `not_configured`; при достаточной сохранённой телеметрии расчёт всё же может выполниться, а проблема источника отобразится оператору.

### Шаг 8. Первая проверка и штатный ежедневный запуск

1. Загрузите тестовые Excel-книги из `data/` через секцию дашборда **«Загрузить Excel и проверить скважину»**. Выберите правильный профиль для каждой книги: DARS, ХИМИК или ERA.
2. В списке выберите `DEMO-001` и нажмите **«Рассчитать риск и получить справку ИИ»**. После проверки откройте BI-рейтинг и карточки сравнения моделей/справки.
3. Для автоматического ежедневного цикла настройте реальные источники, проверьте текущие ID скважин, затем активируйте workflow в n8n. Рискованные скважины и статусы источников проверяйте на странице `/dashboard`.

Демо-книги синтетические. Они нужны для проверки импорта, нескольких листов, цветов классов, пропуска при нехватке данных и UI. Они **не содержат реальных отказов и не годятся для выбора производственных работ**.

## 3. Обязательные поля и остановка расчёта

Требования различаются для импорта и для готовности модели:

| Данные | Обязательно при загрузке | Минимум для анализа по текущему `.env` | Что делает система |
| --- | --- | --- | --- |
| DARS / ХИМИК telemetry | `timestamp` и `well_id` (колонка или поле формы); хотя бы один числовой/логический показатель в строке | 8 разных временных отметок; не менее 8 в окне 28 дней; 2 разных показателя из списка ниже в пределах 7 дней; последний замер не старше 48 часов | При недостатке моделей и ИИ не запускает, выводит недостающие данные |
| Показатели для readiness | Каждая строка может иметь пропуски, но минимум 2 показателя должны быть актуальны | Любые 2 из: `water_cut_pct`, `co2_pct`, `chlorides_mg_l`, `inhibitor_efficiency`, `injection_deviation_pct`, `corrosion_rate_mm_year`, `wall_thickness_mm`, `initial_wall_thickness_mm`, `metal_loss_mm`, `corrosion_load` | Ошибки физических диапазонов и свежести отражаются в качестве данных |
| ERA — история | Дата события и `well_id`; далее тип `work`/`failure` или описание, из которого тип можно определить | Не обязательна для запуска правил риска | История полезна для контекста и рекомендаций ИИ; отсутствие истории показывается как пробел |
| Расписание бригад | Если подключено — корректный JSON и обязательные `crew_id`, `source_id`; даты интервалов ISO 8601 | Не обязательно для математического риска | LLM говорит, что расписание неизвестно, если его нет; не выдумывает бригаду |

Значения должны быть конечными числами в исходных единицах: проценты — `%`, хлориды — `мг/л`, скорость — `мм/год`, стенка — `мм`, эффективность ингибитора — доля `0..1`. DQ sanity bounds: вода `0..100%`, CO₂ `0..8%`, хлориды `0..80000 мг/л`, ингибитор `0..1.2`, отклонение закачки `0..60%`, скорость коррозии `0..1.5 мм/год`, стенка `0.8..14 мм`. Эти границы — проверка правдоподобия входа, не безопасные эксплуатационные пределы.

Изменяемые пороги готовности: `MAI_MIN_TELEMETRY_RECORDS`, `MAI_MIN_TREND_OBSERVATIONS`, `MAI_TREND_WINDOW_DAYS`, `MAI_MIN_CURRENT_SIGNALS`, `MAI_MAX_FORWARD_FILL_DAYS`, `MAI_MAX_TELEMETRY_AGE_HOURS`. Изменяйте с пониманием влияния на DQ, затем пересоздайте `mai-api` и повторите контроль на известных данных.

## 4. Excel: структура, листы и обработка

Поддерживаются `.xlsx` книги до `MAI_MAX_EXCEL_BYTES` (по умолчанию 15 МиБ) и `MAI_MAX_EXCEL_ROWS` непустых строк **на всю книгу** (по умолчанию 10 000). Каждая таблица начинается со строки заголовков; даты можно передать как Excel date/time или ISO 8601. Без временной зоны применяется `MAI_SOURCE_TIMEZONE`.

Для профиля загрузки (`dars`, `khimik`, `era`) используйте листы с одной и той же структурой колонок. Когда имена листов не закреплены в профиле, backend проверяет заголовки всех листов, принимает подходящие и пропускает листы без обязательных колонок. В результате показываются принятые/отклонённые строки, распознанные заголовки и пропущенные листы. Если задать `sheet_names`, должны существовать и подходить все выбранные листы; если задать один `sheet_name`, обрабатывается только он. Для разных строк заголовков можно прописать `sheet_header_rows` по имени листа в `config/source_profiles.json`. Не смешивайте на одном листе несколько таблиц с независимыми заголовками.

ID скважины должен присутствовать в каждой строке или быть передан общим параметром загрузки. Если в файле несколько ID, оставьте поле формы пустым — после импорта дашборд предложит список. Загружайте разные типы данных отдельными файлами с соответствующим профилем. Неизвестные колонки безопасно игнорируются; в ответе загрузки они перечислены. Для импорта используются только поля, перечисленные в профиле.

### DARS и ХИМИК: канонические поля

| Каноническое поле | Обязательно | Тип / единица | Пример внешнего заголовка |
| --- | --- | --- | --- |
| `well_id` | Да, либо поле формы | текст | `well`, `Скважина`, `ID скважины` |
| `timestamp` | Да | дата/время | `date`, `Дата измерения` |
| `water_cut_pct` | Нет, но сигнал для анализа | число, % | `Обводненность, %` |
| `co2_pct` | Нет, но сигнал для анализа | число, % | `CO₂, %` |
| `chlorides_mg_l` | Нет, но сигнал для анализа | число, мг/л | `Хлориды, мг/л` |
| `inhibitor_efficiency` | Нет, но сигнал для анализа | число, доля | `Эффективность ингибитора` |
| `injection_deviation_pct` | Нет | число, % | `Отклонение закачки, %` |
| `corrosion_rate_mm_year` | Нет, но сигнал для анализа | число, мм/год | `Скорость коррозии, мм/год` |
| `wall_thickness_mm` | Нет, но сигнал для анализа | число, мм | `Толщина стенки, мм` |
| `initial_wall_thickness_mm` | Нет | число, мм | `Начальная толщина стенки, мм` |
| `metal_loss_mm` | Нет | число, мм | `Потеря металла, мм` |
| `corrosion_load` | Нет | число по внутреннему контракту | `Коррозионная нагрузка` |
| `water_compatibility_issue` | Нет | да/нет | `Несовместимость вод` |

Поля перечислены как общая схема, но отдельный профиль может распознавать только свои поля. Ненужные служебные колонки не уходят в анализ. Значения CO₂ в долях вместо процентов не исправляйте вручную в каждой выгрузке: настройте `scale_fields` соответствующего профиля.

### ERA: ремонтная история и отказы

Нужны `well_id`, `event_date` и признак типа события. Рекомендуемые колонки: `event_type`, `work_type`, `reason`, `equipment`, `result`, `failure_type`, `cause`, `corrosion_detected`, `repair`, `downtime_days`. Значения типа события из списка в профиле (`work`, `repair`, `maintenance`, `работа`, `ремонт`, `обслуживание`; или `failure`, `incident`, `отказ`, `поломка`, `авария`). Для отказа укажите `failure_type` либо распознаваемый `event_type`; для работы — `work_type` либо распознаваемый тип. История нормализуется в две коллекции: ремонты и отказы.

### Расписание ремонта и бригад: JSON

JSON API возвращает массив записей либо объект `{"crew_availability": [...]}`. Поля одной записи:

```json
{
  "crew_id": "BRIGADE-17",
  "specialties": ["corrosion inspection"],
  "region": "north",
  "status": "available",
  "available_from": "2026-09-29T08:00:00+03:00",
  "available_to": "2026-09-29T20:00:00+03:00"
}
```

Допустимый `status`: `available`, `busy`, `unknown`. Сервис добавляет `source_id` сам. Не передавайте личные данные сотрудников.

## 5. Загрузка и анализ через BI

Откройте `http://localhost:8000/dashboard`:

1. Выберите профиль: DARS, ХИМИК или ERA.
2. При необходимости введите общий ID скважины. Для файла с несколькими скважинами оставьте поле пустым.
3. Выберите `.xlsx` и нажмите **«Загрузить файл»**. Результат покажет принятые/отклонённые строки, использованные листы и причины ошибок.
4. Выберите загруженную скважину в списке и нажмите **«Рассчитать риск и получить справку ИИ»**. Если информации мало, увидите, чего именно не хватает. Риск рассчитывается и без LiteLLM; справка появится, если LiteLLM настроен и скважина удовлетворяет порогу для ИИ.
5. Нажмите **«Выполнить дневной цикл»**, чтобы запросить все настроенные источники для известных скважин, пересчитать рейтинг и создать AI-справки только для рискованных скважин.

BI показывает рейтинг, ошибки/пробелы данных, отдельные результаты каждой зарегистрированной модели, дату последнего расчёта и сохранённый AI-отчёт. Цвета: критический — красный, высокий — оранжевый, умеренный — янтарный, низкий — зелёный, нехватка/ошибка данных — серый.

## 6. Демо-данные для теста

Папка `data/` содержит три книги, в сумме ровно **300 синтетических строк данных** (строка заголовка не включена в подсчёт). В каждой книге два листа, чтобы проверить обработку нескольких вкладок:

| Файл | Листы | Данные | Строк |
| --- | --- | --- | ---: |
| `sample_dars.xlsx` | `SYNTHETIC_DARS_01`, `SYNTHETIC_DARS_02` | 9 скважин × 20 ежедневных телеметрических записей | 180 |
| `sample_khimik.xlsx` | `SYNTHETIC_KHIMIK_01`, `SYNTHETIC_KHIMIK_02` | 8 скважин × 10 лабораторных наблюдений | 80 |
| `sample_era.xlsx` | `SYNTHETIC_ERA_01`, `SYNTHETIC_ERA_02` | 8 скважин, история работ и отказов | 40 |

В DARS намеренно есть DEMO-скважины с низким, умеренным, высоким и критическим классом для проверки цветов. Это искусственно заданные примеры, **не истинные метки риска**. В книгах заголовки ID и даты/времени выделены бирюзовым как обязательные колонки телеметрии; для ERA обязательны ID, дата события и тип события/описание. DQ может показать WARN из-за необязательных сигналов, отсутствующих в отдельных источниках; при этом readiness и расчёт риска проходят. Для ручного испытания загрузите DARS и ХИМИК, затем ERA. Все значения/даты сгенерированы для демонстрации и не описывают реальное оборудование.

## 7. Что делают узлы n8n

В обоих JSON workflow рядом с каждым рабочим узлом расположена заметка на холсте. Таблица ниже объясняет ежедневный путь:

| Узел | Для чего | Вход → выход |
| --- | --- | --- |
| 1. Планировщик | Раз в сутки в 07:00 по часовому поясу n8n | Tick → запуск workflow |
| 2. Загрузка и расчёт риска | Вызывает `POST /api/v1/monitor/run`; backend скачивает DARS/ХИМИК/ERA и расписание для каждого well ID, проверяет readiness, пишет результаты в PostgreSQL | `{horizon_days: 90}` → счётчики, `alerts[]`, статусы источников |
| 3. Проверка риска | Продолжает AI-ветку только при наличии скважин в `alerts[]` | результат мониторинга → true/false |
| 4. Одна скважина на элемент | Даёт отдельный проход для каждой рискованной скважины | `alerts[]` → `{well_id, analysis_id, риск}` |
| 5. Паспорт и история | `GET /api/v1/analysis/runs/{analysis_id}` | ID анализа → сохранённые телеметрия, риск, модели, история |
| 6. Бригады и статусы | `GET /api/v1/monitor/wells/{well_id}/external-data` | ID скважины → расписание и диагностические статусы API |
| 7. Контекст ИИ | Соединяет паспорт и внешний ответ в `AgentWellRequest` | контекст + `external_data` → вход LLM |
| 8. Справка LiteLLM | `POST /api/v1/agent/well`, проверка ответа и сохранение отчёта | структурированные показатели/история/график → JSON-справка в PostgreSQL и BI |

Если `alerts[]` пуст, ветка заканчивается — дашборд уже содержит новые результаты, дополнительных сообщений не отправляется. Если данных недостаточно, модельный расчёт и AI-справка для этой скважины пропускаются, причина остаётся видна в рейтинге. История и расписание не скачиваются самой LLM: backend запрашивает сервисы, валидирует ответы и передаёт LLM только контрактные данные.

`well_analysis_operator.json` выполняет тот же путь по кнопке Form Trigger. У него `responseMode: lastNode`: результат возвращает сам последний узел формы, поэтому узел `Respond to Webhook` не используется.

## 8. Модели риска: подключение и сравнение

### Уже доступные модели

- **Rule Engine** — детерминированные экспертные правила; баллы и класс, не вероятность отказа.
- **Cox** — survival-модель из JSON-артефакта; по умолчанию артефакта нет, поэтому UI показывает `unavailable`, пока вы не положите обученный `models/cox_model.json`.
- **Плагины** — дополнительные зарегистрированные модели через Python entry point-группу `mai_corrosion.risk_models`.

Список/версию/доступность смотрите через `GET /api/v1/risk/models`. Для каждой скважины BI раскрывает отдельные оценки рядом друг с другом: ID и версия, status, горизонт, тип шкалы, probability и отметка калибровки. Нельзя сравнивать численно сырые баллы правил с вероятностью Cox: шкалы различны.

### Добавить модель-плагин

1. Создайте отдельный Python-пакет, копируя `examples/model_plugin_template.py` как исходный каркас. Модель должна получить `ModelInput` (канонические признаки, последние записи, горизонт) и вернуть объект `ModelPrediction` с теми же `model_id`, `model_version`, `horizon_days`, которые объявлены в классе.
2. Реализуйте предобработку точно как при обучении, загрузку зафиксированного артефакта и инференс. На нехватке входных признаков верните `status="insufficient_data"`; на отсутствии корректно загруженного артефакта — `unavailable`. Не подставляйте тестовый score.
3. Укажите plugin entry point в `pyproject.toml` пакета:

```toml
[project.entry-points."mai_corrosion.risk_models"]
my_survival = "mai_my_survival.plugin:MySurvivalModel"
```

4. Соберите wheel пакета и установите его в образ API, добавив в Dockerfile команды копирования wheel и `pip install`, затем выполните `docker compose up -d --build mai-api`. (Если зависимость доступна как закрытый пакет — настройте пакетный registry/секрет сборки; не копируйте токены в Dockerfile.)
5. Проверьте `/health/ready`, затем `/api/v1/risk/models`: модель должна иметь `available: true`. Проверьте анализ на валидном наборе и наличие оценки в BI. Ошибки загрузки entry point отражаются в `plugin_load_errors`.
6. Записывайте в README версии данных, модели, артефакта, горизонты и метрики временной внешней проверки. Сравнивайте прогнозы на одинаковых отложенных скважинах/датах. Endpoint `POST /api/v1/validation/landmarks` считает ROC AUC, PR AUC для score, Brier для probability и сведения о ранней цензуре по переданной разметке. Не называйте вероятность калиброванной без проверки на независимом периоде и репрезентативной разметке.

Контракт разрешает `score_kind`: `probability`, `normalized_score`, `risk_points`, `relative_risk`, `custom`. При вероятности укажите `probability` от 0 до 1; `calibrated: true` разрешён только при наличии probability. Только явно калиброванная probability может вызвать alert по `MAI_ALERT_PROBABILITY_THRESHOLD`; независимые не-вероятностные шкалы остаются для сравнения и не повышают alert автоматически.

## 9. Если во внешнем файле переименовали колонку

Архитектура сохраняется, если меняется только внешнее название, единица и смысл поля остаются прежними. В `config/source_profiles.json` найдите нужный профиль и добавьте новый alias для канонического поля, не меняя канонический контракт. Например:

```json
"co2_pct": ["co2_pct", "co2, %", "массовая доля CO2, %"]
```

Если новое значение — доля `0..1`, добавьте множитель в `scale_fields` для соответствующего профиля, затем проверьте результат на примере строки и перезапустите `mai-api` (конфигурация монтируется read-only с хоста). Не меняйте API/feature/model контракты из-за простого переименования исходной колонки.

Если поле имеет новое физическое значение или единицу, требуется полное версионированное изменение: определить canonical name и единицу → валидацию/диапазон DQ → преобразование и происхождение признака → диагностику/правила → подготовку обучения и артефакта каждой затронутой модели → схемы API/дашборда → fixture и документацию. Не переиспользуйте старое имя для другого смысла; сохраняйте исходное значение/конверсию прозрачно и выпускайте проверенную версию контракта.

## 10. Подключить API с нестандартным форматом

Если внешний сервис не возвращает книгу `.xlsx` по `GET ?well_id=...`, создайте пакет с entry point-группой `mai_corrosion.sources`. Реализуйте `fetch_for_well(well_id, profile)`. Он возвращает bytes книги либо канонический объект:

- телеметрия: `{"records": [{"timestamp": "...", "co2_pct": 1.2}]}`;
- история: `{"work_history": [...], "failure_history": [...]}`;
- расписание: список либо `{"crew_availability": [...]}`.

Смотрите `examples/source_adapter_template.py`. Названия внутри JSON должны быть уже каноническими; далее Pydantic валидирует типы и диапазоны. Укажите `adapter` в нужном профиле, установите пакет в API-образ и пересоберите контейнер. Секреты и схема авторизации остаются в секретном окружении; не логируйте тело ответа с конфиденциальными данными.

## 12. Настройки и диагностика

Главные переменные окружения задокументированы в `.env.example`: PostgreSQL, пороги readiness, лимиты Excel, список скважин, alert-порог, ключ API, LiteLLM, endpoint/token каждого источника, часовой пояс и версия n8n. После изменения `.env` пересоздайте нужный сервис.

Логи и состояние контейнеров:

```powershell
docker compose ps
docker compose logs --tail 100 mai-api
docker compose logs --tail 100 n8n
```

Частые причины:

- `not_configured` — нет `MAI_SOURCE_*_URL`; задайте URL или загрузите соответствующий файл вручную.
- `unavailable` / HTTP 404 — источник отвечает, но у него нет выгрузки для данного ID; проверьте идентификатор и наличие выгрузки.
- `error` — проверьте доступность URL из контейнера, токен, формат файла, листы, названия/единицы колонок и статусы в BI.
- `skipped_insufficient_data` — readiness не прошёл; следуйте конкретному списку полей/дат в ответе и не трактуйте скважину как низкий риск.
- `LiteLLM not configured` — задайте URL и имя модели, проверьте ключ; анализ риска отдельно остаётся в BI.
- `plugin_load_errors` — entry point, имя класса или установка wheel в API-образ не совпали.
- Ошибка подключения PostgreSQL — убедитесь, что контейнер `postgres` healthy и URL указывает на правильные пользователя/БД.

# Контракт внешних источников

Backend запрашивает внешние системы по каждой скважине во время ручного или ежедневного запуска. История ремонтов и текущее расписание извлекаются сервисами данных; LiteLLM получает уже подготовленный контекст и никогда не читает исходный Excel самостоятельно. Секреты хранятся в `.env`, не в workflow.

## Поддерживаемые ответы

| Профиль | Ответ API | Что хранится |
| --- | --- | --- |
| `dars` | Excel `.xlsx`, один файл на `well_id` | Временные отметки и выбранные показатели телеметрии |
| `khimik` | Excel `.xlsx`, один файл на `well_id` | Измерения химического состава и коррозии |
| `era` | Excel `.xlsx`, один файл на `well_id` | История работ и отказов |
| `crew_schedule` | JSON-массив или `{ "crew_availability": [...] }` | Доступность, специализация, регион и интервал бригады |

Общий HTTP-коннектор делает `GET <URL>?well_id=<ID>`, передаёт `Accept` и, если токен задан, `Authorization: Bearer <token>`. Excel должен находиться непосредственно в теле ответа. `404` означает, что выгрузки для скважины нет. Для иной авторизации, HTTP-метода, параметров или envelope добавьте Python-адаптер `mai_corrosion.sources` (см. `README.md`).

## Excel и несколько листов

Настройки расположены в `config/source_profiles.json`: `field_map` хранит алиасы внешних заголовков, `required_columns` — минимальные заголовки, `scale_fields` — множители единиц.

Если `sheet_name`/`sheet_names` не заданы, backend автоматически выбирает листы с обязательными заголовками; остальные листы пропускаются. Все выбранные листы одной книги должны иметь одинаковую структуру колонок. `sheet_name` выбирает один лист, `sheet_names` — список точных имён. `sheet_header_rows` позволяет указать номер строки с заголовками отдельно для каждого листа. Максимум `MAI_MAX_EXCEL_ROWS` строк применяется ко всей книге; размер книги ограничен `MAI_MAX_EXCEL_BYTES`.

Для телеметрии обязательны время и ID скважины (в таблице либо общей форме), а в каждой строке — хотя бы один показатель. Требования к минимальному количеству свежих измерений для запуска моделей описаны в README. В дальнейший анализ передаются только канонические поля: `timestamp`, `water_cut_pct`, `co2_pct`, `chlorides_mg_l`, `inhibitor_efficiency`, `injection_deviation_pct`, `corrosion_rate_mm_year`, `wall_thickness_mm`, `initial_wall_thickness_mm`, `metal_loss_mm`, `corrosion_load`, `water_compatibility_issue`. Лишние колонки игнорируются, исходная книга не хранится.

Единицы: проценты `0..100`, хлориды мг/л, скорость коррозии мм/год, толщина стенки мм, эффективность ингибитора — доля. Если CO₂ задан долей `0..1`, настройте `scale_fields` соответствующего профиля. Для переименования заголовка достаточно добавить alias к прежнему canonical field; для изменения смысла/единицы обновляйте канонический контракт, DQ и затронутые модели.

Профиль `era` принимает события `work` и `failure` (русские и английские алиасы заданы в JSON). Для события нужны дата, тип/описание и ID. Время без временной зоны интерпретируется в `MAI_SOURCE_TIMEZONE`, по умолчанию `Europe/Moscow`, затем сохраняется в UTC. Формулы должны иметь сохранённое Excel-значение.

## Workflow без email

- `well_analysis_operator.json`: Form Trigger → API sync/readiness → анализ → расписание → LiteLLM → ответ формы и сохранение в PostgreSQL. Ответ формы использует `lastNode`; `Respond to Webhook` не нужен.
- `scheduled_risk_monitor.json`: ежедневный расчёт → продолжение только для рискованных скважин → паспорт/история → бригады → LiteLLM → отчёт в BI. Email-узлов нет.

Каждый блок имеет рядом заметку с назначением, входом и выходом. При `MAI_API_KEY` создайте в n8n Header Auth credential `X-API-Key` и назначьте узлам HTTP Request. Результат работы и ошибки источников смотрите на `/dashboard`.
